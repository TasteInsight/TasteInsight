# 环境配置与部署

本文档说明 TasteInsight 的开发、容器运行、生产部署和冷启动配置。各子项目 README 只保留常用命令。

## 工具链

三个子项目、CI 和 Docker 构建统一使用 pnpm 11.21.0，要求 Node.js 22.13 或更高版本。各子项目通过 `packageManager` 固定包管理器版本；依赖安装使用已提交的锁文件。

本机已有其他 pnpm 版本时，可在子项目目录使用 `npx --yes pnpm@11.21.0 <命令>`，无需替换全局 pnpm。CI 与 Docker 使用固定版本，不跟随 `latest`。

小程序的 TypeScript 7／TS6 兼容层、Jest 转换补丁、Markdown 与 SSE 解析依赖统一记录在[小程序依赖维护](../frontend-miniapp/README.md#发布构建与依赖维护)。在 `frontend-miniapp` 中执行 `pnpm type-check` 可运行核心 TS 模块及 Vue 模板、脚本和测试的检查。

## 配置原则

| 运行方式 | Compose / 命令 | 配置入口 |
|---|---|---|
| 完整单机容器栈，本地或服务器 | `docker-compose.yml` | 从后端 `.env.production.example` 创建私有文件，显式 `--env-file` |
| 部分或全部外部基础设施 | 主编排 + `docker-compose.external.yml` | 外部连接地址；按需保留 `local-db` / `local-redis` profile |
| 宿主机热更新，容器运行基础设施 | `docker-compose.local.yml` + `pnpm start:dev` | 后端 `.env.example` → `.env` |
| 后端 E2E | 测试命令 | `.env.test.example` → `.env.test`，独立 `_test` 数据库 |
| 前端开发 | 各自开发命令 | 内置本地默认地址；覆盖写入 `.env.development.local` |
| 管理端发布 | `pnpm build` | 默认 `/api/v1`；覆盖写入 `.env.production.local` |
| 小程序 / App / H5 发布 | 对应 build 命令 | `.env.example` → `.env.production.local`，填写 API 基址 |

默认主编排启动完整单机栈，无需选择数据库或 Redis profile。Compose 需要 2.24.4 或更高版本。外部服务覆盖仅在显式指定时生效；主编排始终读取同目录的 `docker-compose.local.yml` 作为基础设施定义。单独复制部署文件时保留这两个文件，自动部署流程同步分发二者。应用配置可来自任意受保护的 env 文件；文件名与运行机器、部署用途独立。

后端模板保留常用必填项。微信、短信、上传存储、通知、AI、嵌入和调优配置集中在 [环境变量参考](环境变量参考.md)，按需加入当前私有文件。

后端密钥、数据库口令等放在被 Git 忽略的 `.env`、`.env.production` 或 `.env.test`。本地 E2E 测试使用独立数据库，配置和准备步骤见 [后端测试说明](../backend/TEST.md)。`VITE_*` 会被打进前端产物，只能存放公开配置，不能存放密钥。

本地 Nest 开发命令固定 `NODE_ENV=development`，开发 `AppModule` 合并各角色能力并读取 `backend/.env`；本地 Compose 从同一文件取得 PostgreSQL 和 Redis 参数。生产命令与镜像固定 `NODE_ENV=production`，ConfigModule 不读取任何 `.env` 文件。生产 Compose 使用 `--env-file .env.production` 解析一份运维配置，各服务的 `environment` 映射只选取自身消费的字段，不整份注入文件。也可将 `--env-file` 指向其他受保护的配置路径，无需另建角色配置文件。

Shell 中的同名变量优先于文件。数据库原始凭证在四个后端角色和 PostgreSQL 服务之间同步，Redis 口令在两个 API、worker 和 Redis 服务之间同步；必填凭证与两个 origin 缺失或为空时，Compose 配置检查失败。可选字段未设置时不会进入容器环境，保留应用默认值；显式空字符串会原样传入，不等同于省略。模板列出必填配置与首次管理员入口，可选能力和默认调优项由参考文档统一说明。

后端、Docker 入口、Prisma CLI 和维护脚本共用数据库连接解析：显式 `DATABASE_URL` 优先；省略时使用 `POSTGRES_*` 生成经过 URL 编码的连接串。完整连接串保留自定义查询参数；显式空连接串会报错。已有配置同时包含两种形式时，核对 `DATABASE_URL` 的实际目标；使用原始参数时移除该覆盖值。各 Nest 应用根模块绑定自身的配置校验，在数据库、队列及业务 provider 初始化前完成检查；直接运行生产入口也经过同一校验，无需配置额外的角色变量。生产迁移与首次初始化仅由独立的 `migrate` 作业执行。Python 嵌入容器只接收 Compose 明确列出的 `PYTHON_EMBEDDING_*` 和 `HF_ENDPOINT` 变量。

`NODE_ENV` 只接受 `development`、`test`、`production`，未知值启动失败。宿主机生产进程需由服务管理器或部署环境注入配置，不能依赖 `start:prod` 自动加载 `.env.production`。测试命令加载 `backend/.env.test` 或使用 CI 显式注入；测试模式不读取开发 `.env`。所有 E2E 入口在应用模块导入前检查 `NODE_ENV=test` 与独立的 `_test` 数据库目标；测试准备脚本在任何副作用前执行相同校验。继承的非测试库地址会使测试失败，单元测试不需要准备数据库。

### 启动校验与浏览器来源

生产配置按实际入口校验：

| 角色 | 必填连接与凭据 | 可选能力与配置边界 |
|---|---|---|
| `public-api` | 数据库、Redis、JWT access / refresh 密钥、公共 `APP_URL` | 推荐、上传、通知 webhook URL、内容审核；登录渠道开关、短信、邮箱、校园 OAuth 与 AI 配置由此角色消费 |
| `admin-api` | 数据库、Redis、JWT access / refresh 密钥、公共 `APP_URL` | 推荐管理、上传、通知 webhook URL、内容审核配置与私有图片预览 |
| `worker` | 数据库、Redis | 推荐及嵌入配置、webhook URL / 签名密钥 / 投递参数、内容审核凭据与公共图片根地址，以及共享上传存储配置 |
| `migrate` | 数据库 | 可选首次管理员凭据；不要求 Redis、JWT、origin、上传或业务集成配置 |

常规数据库配置使用 `POSTGRES_USER`、`POSTGRES_PASSWORD`、`POSTGRES_DB`、`POSTGRES_HOST` 和 `POSTGRES_PORT`，可选 `POSTGRES_SSLMODE`。高级连接参数可通过完整 `DATABASE_URL` 覆盖应用连接；主编排仍要求 `POSTGRES_*` 凭据来解析内置数据库定义。URL 必须包含 PostgreSQL 账号、密码与数据库名；Redis 与数据库口令不能保留示例占位值。Compose 解析完整编排时会检查文件中所有必填插值，即使只选取某个服务；独立运行迁移入口只需迁移角色的配置。

完整 Compose 与生产网关要求 `APP_URL` 和 `ADMIN_APP_URL` 为两个不同 DNS 主机名的 HTTP(S) origin，不能包含路径、查询参数、凭据或片段；非默认端口写入 origin。独立 API 进程仅强制提供公共 `APP_URL`；提供 `ADMIN_APP_URL` 时会校验并将其加入 CORS 来源。独立宿主机后端的 `APP_URL` 基路径兼容性不改变网关的此项约束。公共 API 的微信小程序 `WECHAT_APPID` 与 `WECHAT_SECRET` 为成对可选配置：两项都未设置或留空可启动；配置任一项时必须同时提供另一项。启动校验不请求微信接口验证账号。

两个 API 使用的 `JWT_SECRET` 和 `JWT_REFRESH_SECRET` 必须互不相同、至少 32 字节且不是模板占位值。开发、测试、生产使用独立密钥；长度校验不能证明随机性，应使用安全随机生成器。配置校验不能识别其他部署误复用的未知密钥。已有生产密钥符合要求时可保留，本规则不增加 issuer、不强制现有用户退出。初始管理员凭据只注入 `migrate`，已有部署可省略；提供的密码至少 12 字符，禁止示例占位和明显默认密码。首次部署缺少初始账号时会记录管理端不可用警告。

`AUTH_LOGIN_METHODS` 仅注入公共 API，取值为逗号分隔的 `phone`、`wechatMiniapp`、`wechatApp`、`campusOAuth`。省略时仅允许两类微信登录，手机号须显式选择；设为空字符串时关闭全部登录方式。白名单与对应渠道凭据共同决定能力接口和服务端授权。调整白名单后重新创建公共 API 进程，校园身份认证配置和已有用户会话保持独立。

`CAMPUS_VERIFICATION_METHODS` 独立控制校园身份认证方式，支持 `campusEmail` 和 `campusOAuth`，默认启用两种方式，空字符串关闭全部校园认证方式及登录后的自动认证。每种方式还需配置对应服务商。关闭方式后，服务端拒绝新的发起请求及未完成的验证码或 OAuth 确认请求；已取得的身份认证按其原有效期和审核状态生效。

例如：

```dotenv
AUTH_LOGIN_METHODS=wechatMiniapp,wechatApp,campusOAuth
CAMPUS_VERIFICATION_METHODS=campusEmail,campusOAuth
```

`GET /auth/capabilities` 分别返回 `loginMethods` 和 `verificationMethods`；原扁平字段保留供已安装客户端使用。校园 OAuth 登录通过登录凭据识别账号；同时开启校园 OAuth 认证时，登录流程依据校方可信在读声明更新学生资格，缺少可信在读信息时进入待审核状态。关闭校园 OAuth 认证后，登录保留已有校园资格及其有效期。校园资格已有其他账号归属时，登录保留原归属及当前账号的资格状态。管理员已审核的状态在登录时保留。校园邮箱验证提交认证申请，审核通过后获得学生资格。

校园 OAuth 登录使用 `POST /auth/campus/oauth` 发起，沿用 `CAMPUS_OAUTH_REDIRECT_URI` 回调，客户端通过 `POST /auth/campus/login` 提交一次性确认码及发起设备的 `loginVerifier`。校园账号通过 `UserIdentity` 中的登录凭据关联食鉴账号。校园认证记录保存在 `StudentVerification`，用于学生资格及权限判断。用户可在“登录方式”中单独绑定校园账号，对应 `POST /user/identities/campus/oauth` 和 `POST /user/identities/campus/oauth/complete`。绑定受登录方式开关控制，只更新登录凭据；校园认证入口只更新校园资格。H5 使用授权弹窗，Android 使用系统浏览器，微信小程序使用独立 web-view 登录页；小程序需配置校方授权及 API 回调域名为业务域名。回调页提供一次性确认码供返回应用后确认，确认码有效期为 3 分钟。

配置失败仅输出字段与规则。修复注入值后重新启动；不要将秘密粘贴到日志或工单。具名存储实例在启动时校验；默认实例为 `s3` 时检查通用 `S3_*` 必填项；AI 配置继续在实际调用处检查。

### 统一内容审核

管理端“全局配置”的统一内容审核默认为关闭状态，已有业务审核规则继续生效。启用后选择阿里云内容安全或微信小程序内容安全，并选择审核方式：

| 审核方式 | 发布流程 |
|---|---|
| 人工审核（`manual`） | 内容进入人工队列，由管理员确认 |
| 机器审核（`machine`） | 文本和全部图片均通过后发布；复核结论进入人工队列 |
| 机器审核后人工审核（`machine_and_manual`） | 机器通过后继续由管理员确认 |

菜品资料提交保留业务确认环节，机器通过后仍进入菜品资料审核。个人资料修改作为草稿审核，公开昵称、简介和头像在通过前继续使用当前值。审核服务返回违规结论时执行拒绝；服务异常、身份条件未满足及未知结果交人工处理。任务和逐项结果保存在数据库，worker 重启后继续处理；微信图片等待回调超过 31 分钟进入失败队列，供管理员人工复核。切换服务商或方式用于新建任务，已有任务按保存的策略执行。

人工和机器审核均需设置 `MODERATION_MEDIA_SECRET` 与 `MODERATION_PUBLIC_BASE_URL`，用于私有图片的限时签名预览。前者使用至少 32 个字符的独立随机密钥，可通过 `openssl rand -hex 32` 生成；后者填写公网可访问的 API 根地址。宿主机开发使用 `http://localhost:3001`。生产示例为 `https://api.example.com/api/v1`，网关将 `/api/v1/` 前缀剥离后转交公共 API。`APP_URL` 继续填写 `https://api.example.com` 这类 origin。

阿里云接入需开通内容安全增强版并授权 AccessKey 调用，配置 `MODERATION_ALIYUN_ACCESS_KEY_ID` 和 `MODERATION_ALIYUN_ACCESS_KEY_SECRET`。默认地域 `cn-shanghai`，文本服务 `comment_detection`，图片服务 `baselineCheck`。默认通用文本服务每次上限为 600 字，超过上限的整段文本进入人工审核；文本等级读取 `Reason` 中的 `riskLevel`，图片等级读取 `RiskLevel`。高风险拒绝，中风险复核，低风险和无风险通过。服务名与区域须与已开通的能力对应。协议见[阿里云通用文本审核 API](https://help.aliyun.com/zh/document_detail/434034.html)和[图片审核增强版同步 API](https://www.alibabacloud.com/help/zh/content-moderation/latest/image-review-enhanced-api)。

微信接入使用 `WECHAT_APPID`、`WECHAT_SECRET` 和消息推送配置中的 `MODERATION_WECHAT_TOKEN`、`MODERATION_WECHAT_AES_KEY`，消息推送选择安全模式。将微信服务器配置的 URL 设为 `MODERATION_PUBLIC_BASE_URL` 后追加 `/content-moderation/wechat/callback`；生产示例为 `https://api.example.com/api/v1/content-moderation/wechat/callback`。服务器需能向 `api.weixin.qq.com` 发起 HTTPS 请求，并满足微信后台的调用 IP 白名单要求。后端通过稳定版令牌接口的普通模式复用令牌。

微信 v2 文本和图片审核要求用户拥有当前 AppID 下已绑定的 OpenID，并在近两小时访问过小程序。手机号、校园登录或原生 App 登录产生的账号在缺少该身份时进入人工审核，既有身份关系保持原状。微信文本上限为 2500 字，超长文本进入人工审核；图片上限为 10 MB，媒体链接需能被微信服务器下载。图片审核为异步流程，官方回调窗口为 30 分钟。具体条件见[微信文本安全接口](https://developers.weixin.qq.com/miniprogram/dev/server/API/sec-center/sec-check/api_msgseccheck.html)、[多媒体安全接口](https://developers.weixin.qq.com/miniprogram/dev/server/API/sec-center/sec-check/api_mediacheckasync.html)及[稳定版令牌接口](https://developers.weixin.qq.com/miniprogram/dev/server/API/mp-access-token/api_getstableaccesstoken.html)。

审核中图片通过 `/content-moderation/images/:id` 的限时签名地址提供给检测服务和管理员。本地存储的暂存文件位于上传目录的 `.moderation` 子目录，应用静态路由与生产网关对 `/images/.moderation/` 禁止直接访问。云端暂存对象位于 `moderation-private/`，由实例配置的对象 ACL 或桶策略保持私有，普通图片按 `images/*` 前缀授权公开读取；若配置 CDN、代理或存储公共读取策略，应同步保留该路径的私有访问规则。对外连通性检查应覆盖签名图片下载、微信回调验证与结果推送。

审核规则在数据库中更新，客户端继续使用现有接口读取状态。密钥、回调配置、图片根地址、存储实例或默认实例配置变化后，重新创建 `public-api`、`admin-api` 与 `worker`，使三者使用同一组参数；新增配置说明见[环境变量参考](环境变量参考.md#统一内容审核)。Compose 渲染、单元测试与进程健康检查覆盖配置和本地逻辑，真实审核账号的权限、配额、网络和端到端回调另行验收。

`NOTIFICATION_WEBHOOK_URL` 同时注入两个 API 和 worker，使通知生产端与投递端使用一致的外推开关。URL 省略或为空时仅保留站内收件箱；设置时必须符合 HTTPS 规则。`NOTIFICATION_WEBHOOK_SECRET` 与轮询、超时、重试参数仅注入 worker，由 worker 校验签名密钥和投递参数。生产安全开关 `RUN_SEED`、`IMPORT_DATA`、`ENABLE_MOCK_AUTH` 在所有角色中检查，不能通过切换入口绕过。

`CORS_ALLOWED_ORIGINS` 是逗号分隔的精确 HTTP(S) origin，不能包含通配符、路径、查询参数、片段或 URL 凭据。`APP_URL` 和 `ADMIN_APP_URL` 的 origin 自动允许；开发模板包含 `localhost:5173` 与 `localhost:5174`，临时 E2E 来源写入独立测试配置。没有 Origin 的原生与微信请求仍可访问 API，业务鉴权继续要求 bearer JWT；浏览器跨域请求不启用 cookie credentials。CORS 不替代鉴权。

### 测试登录隔离

前端测试登录约定为 `VITE_ENABLE_TEST_LOGIN=true`，仅 Vite `development` 或 `e2e` mode 可启用；生产或其他发布 mode 开启时应构建失败。后端另需 `ENABLE_MOCK_AUTH=true` 且 `NODE_ENV=development` 或 `test`。两个开关缺省关闭，各自独立授权；优化构建与 Vite mode 不等同于后端运行环境。

后端保留 E2E mock code 协议，但关闭开关时直接拒绝这些 code，不向微信发请求；真实微信接口失败不会回退为测试身份。测试身份获得正常签名 JWT，业务接口仍经过原有 guard。生产开启 `ENABLE_MOCK_AUTH` 会在启动阶段失败。

对话服务支持 `AI_PROVIDER=openai`。`AI_PROVIDER`、`AI_API_KEY`、`AI_MODEL`、`AI_BASE_URL` 按环境变量、数据库配置、代码默认值的顺序取值。模板不设置 `AI_MODEL`，允许管理端数据库配置生效；两处均未设置时使用 `gpt-4o-mini`。其他 provider 名称会在发起对话前报错。

宿主机映射端口与容器内端口是两组变量：

- 本地后端和本地 Compose 共享 `REDIS_PORT`、`POSTGRES_PORT`，分别用于连接地址和宿主机映射端口；容器内 Redis / PostgreSQL 固定监听 `6379` / `5432`。
- 完整单机容器栈默认通过服务名和容器内部端口通信。
- 旧 `REDIS_EXPOSE_PORT` / `POSTGRES_EXPOSE_PORT` 仅在对应新端口变量未设置时作为映射端口回退。
- 后端监听端口由 `PORT` 指定。

## 可选公众号采集

## Docker 生产部署

### 进程与域名

同一后端镜像包含四个入口；业务服务和数据库模型在仓库中共享：

| 服务 | 入口 | 职责 |
|---|---|---|
| `public-api` | `node dist/src/main.public` | 用户登录、浏览、评价、推荐、用户上传等 HTTP |
| `admin-api` | `node dist/src/main.admin` | 管理员登录、审核、配置和管理 HTTP |
| `worker` | `node dist/src/main.worker` | 队列消费者与通知调度；仅提供内部健康检查 |
| `migrate` | `node dist/src/main.migrate` | 执行 Prisma 迁移、首次管理员及系统模板初始化，成功后退出 |

三个常驻角色不执行迁移、seed、目录导入或首次初始化。所有角色使用同一数据库与兼容的 schema；同一版本只需一个迁移作业。发布顺序、schema 兼容性和回滚边界需要共同管理，进程可以分别扩容，不意味着数据库可以独立演进。

`APP_URL` 始终指向用户 API 的公网 origin，两个 API 和网关保持相同值；图片默认生成在 `APP_URL/images`。`ADMIN_APP_URL` 指向管理站点 origin。worker 与迁移作业不接收这两个地址。管理端构建继续使用相对路径 `/api/v1`，不需要针对每个域名重建前端。

```text
APP_URL
  /api/v1/* -> public-api:3000/*
  /images/* -> uploads_data
  其他路径（含 /、/login） -> 404

ADMIN_APP_URL
  /api/v1/* -> admin-api:3000/*
  /werss/*  -> werss:8001/*（可选，转发时去除前缀）
  /*         -> frontend:80

worker -> PostgreSQL / Redis / 队列与调度
migrate -> 迁移与初始化 -> public-api / admin-api / worker
```

用户域名不会转发到管理 API，也不会将 `/`、`/login` 或其他路径跳转到管理站点。HTTP 到同一用户 API origin 的规范 HTTPS 跳转仍受支持；它不会改变为管理域名。未知 HTTP Host 被拒绝；启用 TLS 时，未知 SNI 的握手也被拒绝。用户 API 的校园 OAuth 回调关闭访问日志并发送 `no-store`、`no-referrer`，HTTP 到 HTTPS 的该回调跳转沿用同样规则。

`backend/nginx.conf`、`backend/nginx.https.conf.template` 是 HTTP/TLS 入口模板，`nginx.common.conf`、`nginx.public.conf`、`nginx.admin.conf` 与可选的 `nginx.werss.conf` 片段组织上游、健康探测和域名路由。`gateway-render.sh` 在 Nginx 官方镜像启动时校验 origin，只替换列明的配置变量，保留 `$host`、`$request_uri` 等 Nginx 变量。不要将未渲染的模板直接挂为生效配置。`frontend-web/nginx.conf` 只负责静态文件、SPA 回退和缓存。

网关上游使用 Docker DNS `127.0.0.11`、共享 upstream zone 与 `resolve`，容器重建和副本地址变更不依赖旧 IP。该功能要求 Nginx 1.27.3 或更新版本，默认镜像为 `nginx:1.28-alpine`，可通过 `NGINX_IMAGE` 选择满足要求的版本。参考 [Nginx upstream 文档](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#server)。

### 全新部署

启用可选 WeRSS 时，采用 [微信公众号新闻同步](./微信公众号新闻同步.md#完整-compose-部署) 中的首次部署步骤：先启动应用和网关，再通过管理域名授权，最后加载 AK/SK。以下命令适用于默认服务栈。

准备两个域名的 DNS；直接终止 TLS 时准备覆盖两个域名的证书。复制环境示例后，替换全部占位密码及启用能力的凭据：

```bash
cd backend
cp .env.production.example .env.production
chmod 600 .env.production
# 编辑 APP_URL、ADMIN_APP_URL、TLS 配置、数据库与身份凭据

# 只构建一次后端镜像，其他角色复用相同镜像标签

docker compose --env-file .env.production logs -f public-api admin-api worker nginx
```

`migrate` 先等待 PostgreSQL 健康，再通过 `node dist/src/main.migrate` 完成迁移和初始化；三个角色通过 `service_completed_successfully` 等待该作业，并继续等待各自的 Redis 等依赖。迁移成功后调用共享 `DatabaseInitializer`。管理员表为空时使用 `INITIAL_ADMIN_USERNAME` / `INITIAL_ADMIN_PASSWORD` 创建首个超级管理员，已有管理员和密码保持不变。全新部署需取消这两项的注释并设置安全凭据；已有部署可保持省略。系统模板幂等同步，显式全局配置不被覆盖，也不从模板默认值自动创建。首次登录后修改密码并移除环境中的初始密码。

生产 PostgreSQL、Redis、前端、API 和 worker 均通过内部网络访问，Nginx 发布站点端口。可选 WeRSS 另有仅绑定宿主机回环地址的排障端口。内部 `/health` 检查不执行初始化；网关在回环地址分别探测用户 API、管理 API 和前端。检查成功只证明进程与受检依赖就绪，不覆盖真实账号、短信、微信、校园认证及其他外部服务。

### HTTPS 与外部反向代理

| 配置 | 含义 |
|---|---|
| `GATEWAY_TLS_MODE=on` | Nginx 监听 TLS，两个 origin 均须使用 HTTPS |
| `GATEWAY_TLS_MODE=off` | Nginx 仅监听 HTTP，可用于本地 HTTP 或外部代理终止 TLS |
| `TLS_CERTS_PATH` | 宿主机证书目录，只读挂到 `/etc/nginx/tls` |
| `TLS_CERT_FILE` / `TLS_KEY_FILE` | 目录内的完整证书链和私钥文件名，默认 `fullchain.pem` / `private.key` |
| `HTTP_PORT` / `HTTPS_PORT` | 网关宿主机端口；关闭 TLS 后 443 容器端口没有监听器 |

示例 origin 为 `https://api.example.com` 和 `https://admin.example.com`。自建部署替换域名即可，不需要修改 TypeScript、Nginx 模板或前端源码。若使用非标准 HTTPS 端口，origin 和 `HTTPS_PORT` 应相符。

已有 acme.sh 可以继续向原共享证书目录安装证书，将 `TLS_CERTS_PATH` 指向该目录。保留现有续签任务和账号；续签成功后运行 `docker compose --env-file .env.production exec -T nginx nginx -t`，再执行 `docker compose --env-file .env.production exec -T nginx nginx -s reload`。不要把私钥复制到仓库或镜像。目录挂载允许续签工具以替换文件的方式更新证书。

外部负载均衡器终止 TLS 时使用 `GATEWAY_TLS_MODE=off`，两个 origin 仍填写外部 HTTPS 地址。代理必须保留目标 Host，私网或防火墙应限制网关 HTTP 端口只接受可信入口。传给应用的 `X-Forwarded-Proto` 由各 origin 的 scheme 生成，不信任客户端任意提供的转发协议。通过 `TRUSTED_PROXY_CIDRS` 配置应用实际信任的代理地址；不要使用全网信任范围。公开登录、身份认证及小程序正式版不得使用明文 HTTP。

### 从单一 backend 服务迁移

首次切换前暂停自动发布。保留原 `COMPOSE_PROJECT_NAME`（或原 `-p` 参数）、PostgreSQL / Redis 凭据、JWT 密钥、管理员账号和证书续签配置。修改 PostgreSQL 环境变量不会修改已有卷中的数据库账号。

1. 记录旧 Compose 项目、容器 ID、镜像标签与实际挂载卷。备份旧 Compose、网关及环境配置，使用仅运维账号可读的目录。备份 PostgreSQL 和上传文件；需要数据库与文件的一致快照时，先暂停业务写入并等待后台任务收敛。确认备份在隔离环境可恢复。
2. 核对原卷身份。默认项目 `tasteinsight-production` 对应 `tasteinsight-production_db-data`、`tasteinsight-production_redis-data`、`tasteinsight-production_uploads_data`；使用其他项目名的部署继续使用自己的前缀。新 Compose 保留三个卷键，不新建空库替代原库，不执行 seed / reset。
3. 保存旧发布目录和镜像后，准备新版本文件、两个 origin 与证书挂载。执行 `config --quiet` 和独立的 `nginx -t`。确认迁移与旧应用兼容；不兼容的 schema 变更需要维护窗口。进程拆分本身不需要新增 schema 迁移。
4. 使用新 Compose 启动 `public-api admin-api frontend` 并等待健康，保留旧网关和旧 `backend` 服务。此时新 API 不启动消费者或调度器，旧进程仍处理原有请求和后台工作。不要传 `--remove-orphans`。
5. 明确停止已核对身份的旧 `backend`，等待优雅退出，随后启动新 `worker` 并等待健康。两个后台进程不能在切换过程中同时消费与调度。若失败，先停新 worker，再恢复旧进程。
6. 重新创建网关，核对两个域名的证书、公共 / 管理路由、公共 `/` 与 `/login` 的 404、同源 HTTP 到 HTTPS 跳转、图片和 SSE。管理端书签使用独立管理域名。确认数据库、Redis、上传卷身份及关键表计数与迁移前一致。数据验证不需要写入验收账号或生产测试数据。
7. 验收通过后，仅删除已经停止且核对过项目 / 服务标签的旧 `backend` 容器，不删除卷。保留旧发布、备份和镜像用于回滚；随后恢复自动发布。

只改服务名不会迁移数据。项目名错误会选择另一组卷；发现空库、卷名不符或数量异常时停止切换，不用 seed 补数据。

回滚时先停止新 worker，恢复旧版本 Compose、网关、环境配置与镜像，再恢复旧 backend。不得让新旧 worker 同时运行。若发布包含不向后兼容的 schema 迁移，旧程序不能直接恢复，须按该迁移的前滚或备份恢复方案处理。回滚应用不等于回滚数据库。

### 自动部署

`CI - Required Checks` 复用后端、管理端工作流并运行定向部署检查。`dev` 与 `main` 均执行 CI，自动发布仅接受本仓库 `main` 的成功 push 检查，且 SHA 仍为 `main` 当前提交。手动发布选择 `main`；正式 `v*` 标签保留独立生产发布入口，带 `-` 的预发布标签仅保留版本标记。

生产发布使用 `/srv/tasteinsight` 目录，`PROD_DEPLOY_PATH` 可指定其他同结构的部署根目录：

| 路径 | 用途 |
|---|---|
| `shared/.env.production` | 服务器维护的应用配置与凭据，权限设为 `600` |
| `shared/tls/` | 服务器维护与续签的证书，env 中的 `TLS_CERTS_PATH` 指向此目录 |
| `releases/<发布标签>/` | 每次发布的源码、网关模板与镜像版本配置 |
| `current` | 最近一次通过发布健康检查的版本目录软链接 |
| `bin/compose.sh` | 当前版本的 Compose 入口 |

生产 GitHub Actions 使用 `PROD_HOST`、`PROD_USER`、`PROD_SSH_KEY`；`PROD_DEPLOY_PATH` 缺省为 `/srv/tasteinsight`。镜像构建和服务器拉取共用仓库级 Secrets `REGISTRY_HOST`、`ALIYUN_USERNAME`、`ALIYUN_PASSWORD`。SSH 用户需具有部署目录写权限和 Docker 使用权限。应用 env 和证书由服务器维护，CD 上传内容为版本源码包及发布脚本。

发布脚本 `.github/scripts/deploy-production.sh` 读取现有 `current`，继承其中的 `compose.production.yml`、`compose.status.json`、`status.nginx.conf` 和 `ops/`。资源限制、生产网络、状态页和运维入口随版本保留。状态页配置中的绝对挂载路径继续引用原发布目录，发布目录需要保留。版本内的 `compose.release.json` 最后加载，统一指定后端四角色、前端、可选嵌入及 WeRSS 的镜像，覆盖生产配置中固定的应用镜像。

镜像与源码来自同一触发提交，镜像标签包含提交 SHA 和运行 ID，发布目录名额外包含重试次数。重跑失败的生产部署任务时继续使用已构建镜像，并创建新的发布目录。生产项目名保持 `tasteinsight-production`，继续使用原数据库、Redis 和上传卷。首次接入要求已有上述服务器目录与配置，并已完成进程拆分；旧 `backend` 容器会阻止自动发布。

发布依次执行 Compose 配置检查、镜像拉取、网关配置与证书检查、迁移及应用健康检查、网关重建与健康检查。全部通过后安装 Compose 入口并原子切换 `current`。发布保留共享配置、证书、原发布、镜像和数据卷。

发布失败时 `current` 保持原版本，失败目录保留供排查。应用启动或网关更新期间的失败可能留下已更新的容器；此时软链接指向不能代表所有容器版本。按实际容器镜像和迁移结果确定恢复方案，检查 schema 兼容性后再恢复相应角色；数据库迁移成功后的应用回滚仍遵循本节前述兼容性要求。

日常运维使用服务器入口，确保叠加生产资源、状态页和当前镜像配置：

```bash
/srv/tasteinsight/bin/compose.sh config --quiet
/srv/tasteinsight/bin/compose.sh ps
/srv/tasteinsight/bin/compose.sh logs --tail=100 public-api admin-api worker nginx
```

修改共享 env 后重新创建受影响角色；证书续签继续使用 `/srv/tasteinsight/bin/reload-nginx.sh` 完成配置检查和重载。全部发布使用 `production` 环境并串行执行。Actions 仅使用生产 SSH 与镜像仓库 Secrets，开发分支通过 CI 验证后合入 `main` 发布。

### 可选嵌入服务与独立部署边界

默认 `EXTERNAL_EMBEDDING_SERVICE_ENABLED=false`，`embedding-service` 位于可选的 `embedding` profile，不会在默认 Compose 启动中构建、启动或下载模型。启用时同时设置 `EXTERNAL_EMBEDDING_SERVICE_ENABLED=true` 和 `COMPOSE_PROFILES=embedding`。CD 构建设置 `PRELOAD_MODEL=false`；首次启用服务时文本编码器仍需从 `HF_ENDPOINT` 下载到 `huggingface_cache`。空 `PYTHON_EMBEDDING_PRELOAD_MODELS` 仅跳过 v2 / v3 融合层预热。v3 训练权重仍需单独提供，冷启动较慢时调整发布等待时限。

连接地址可分别通过 `POSTGRES_HOST` / `POSTGRES_PORT`、`REDIS_HOST` / `REDIS_PORT`、`EXTERNAL_EMBEDDING_SERVICE_URL` 配置，默认指向单机 Compose 服务。显式 `DATABASE_URL` 优先于原始连接参数；常规模板仅维护 `POSTGRES_*`。容器应用接入外置数据库或 Redis 时，使用仓库提供的 `docker-compose.external.yml`，按需启用 `local-db` / `local-redis` 保留同机服务；具体命令见[独立数据库、Redis 与嵌入服务](#独立数据库redis-与嵌入服务)。外置嵌入服务通过地址与启用开关选择；同机嵌入容器由 `embedding` profile 启动。

该 Compose 是单机编排，项目网络和命名卷不会跨主机共享。将 API / worker 分别迁往其他机器前，需要先配置可访问的数据库与 Redis、受限网络、共享上传存储或云端对象存储，以及指向实际服务的网关上游。上传卷不能作为跨主机共享存储；使用 OSS 或 S3 时核对浏览器图片来源与存储域名。进程拆分不承诺跨主机自动发现、独立 schema 或分布式文件系统。

同机可使用 `--scale public-api=2 --scale admin-api=2` 增加 API 副本；没有固定容器名或应用宿主机端口占用。worker 的扩容必须先审查消费者幂等和调度单实例语义，不能仅照搬 API 的扩容命令。`WORKER_STOP_GRACE_PERIOD` 默认 90 秒，退出时等待已接收任务和资源清理；超时任务仍依赖队列重试与业务幂等。

## 数据安全与维护

`RUN_SEED`、`IMPORT_DATA` 和 `ENABLE_MOCK_AUTH` 缺省为 `false`；生产开启任一项时，所有角色的启动校验均拒绝运行。`prisma/seed.ts` 与 `seed_docker.ts` 会先删除业务数据，不用于上线、普通重启或服务拆分。每次发布的 `migrate` 作业执行幂等迁移与初始化，API / worker 普通重启不重复运行该流程。

需要进入数据库时，从 `backend` 目录运行：

```bash
docker compose --env-file .env.production exec db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

生产上传目录为 `/app/uploads`，两个 API 使用原 `uploads_data` 卷，网关以只读方式挂载并在公共域名的 `/images/` 提供文件。worker 共享上传卷并接收与 API 一致的存储配置，用于按图片实例 ID 清理菜品资料的废弃图片；使用 OSS 或 S3 时，三个进程使用同一存储位置和相应访问凭据。迁移作业保留卷挂载，配置仅包含数据库和首次初始化参数。本地源码运行可配置独立 `UPLOAD_LOCAL_PATH`。

### 维护导入

显式运行 `pnpm run maintenance:import [Excel路径]` 可增量导入食堂、楼层、窗口和菜品；默认文件为 `backend/prisma/DishesofZijingYuan.xlsx`，读取首个工作表。运行前核对进程中的 `DATABASE_URL`、数据库备份和输入文件。维护命令不会通过常规生产启动触发。

- 必填列：`食堂`、`窗口`、`菜品名`、`价格`。价格必须为非负有限数，也接受 `12.5元/份` 等带单位的值。
- 可选列：`楼层`、`窗口编号`、`菜品子项`、`供应时间`、`菜品描述`、`tags`。
- 全部行在创建数据库客户端前完成读取和校验。目录写入在单个 Serializable 事务中执行，失败时整批回滚。
- 已有记录不覆盖；重复导入复用已有目录项。窗口编号参与匹配；本次使用的食堂、楼层、窗口或父菜品无法唯一确定时，报出行号并整批拒绝。其他未使用的重名记录不阻断导入。命令不会清空业务数据或创建测试账号。


## 更新与停止

已完成进程拆分的部署可重新构建镜像并执行“全新部署”中的配置、健康门槛命令，或由自动发布脚本更新。独立更新某个角色时先确认该版本与当前 schema、队列载荷及其他角色兼容；迁移统一执行一次。

停止服务并保留数据库、Redis、上传和模型卷：

```bash
docker compose --env-file .env.production down
```

不要在正常维护中执行 `docker compose down -v`、`docker volume prune` 或生产 seed。首次切换时不使用 `down` 或 `--remove-orphans` 提前移除旧服务。

## 上线验收

- 核对两个 origin、证书链、同源 HTTP 到 HTTPS 跳转、未知 Host 拒绝、API / 管理路由、上传图片和 SSE；公共域名的 `/`、`/login` 与未知路径返回 404，响应不包含指向管理站点的跳转。公共域名不能访问管理接口，管理域名不承载用户登录。
- 使用真实账号验证实际启用的微信、短信、校园 OAuth、校园邮箱及通知服务，核对回调、授权、鉴权和失败重试；未配置的可选能力保持关闭。
- 小程序发布包写入公共 HTTPS API 基址并配置合法域名；原生 App 需实际安装包、签名与目标设备验收。资源编译或 Mock 检查不代表外部服务可用。
- 记录版本、镜像、迁移结果、卷身份和非敏感数据计数，验证隔离恢复与回滚方案；自动化检查和容器健康不能替代业务发布验收。

审核服务默认图片接口按单张图像检测。多帧图片保留原文件并进入人工复核，管理员确认全部画面后发布。
